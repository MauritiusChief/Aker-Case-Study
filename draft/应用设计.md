# 加拿大 Aker 物业经营决策应用方案

## 1. 项目定位

本项目面向资产经理或区域经理，将分散的 Rent Roll 数据整理为一个可下钻、可模拟、可由 LLM 辅助解释的物业经营决策应用。

项目的主要交付目标是招聘 Case Study，而不是完整的生产级物业管理系统。应用重点展示以下能力：

- 将原始业务报表转化为结构化数据和统一指标。
- 从单个 Rent Roll 数据快照动态生成 Unit Availability。
- 从组合层面发现空置和租约到期风险，并下钻到物业和单元。
- 使用透明、可复核的 What-if 模型评估经营假设。
- 让 LLM 调用确定性的统计工具生成 Morning Brief，而不是让 LLM 自行计算或生成 SQL。

核心用户路径为：

```text
Portfolio Overview
  -> 发现高风险物业
  -> 查看 Availability 或 Lease Risk
  -> 选择一组受影响单元
  -> 运行 What-if 模拟
  -> 由 Morning Brief 总结重点和行动方向
```

## 2. 数据范围与基本约定

### 2.1 单月快照

数据库明确只保存一个月份的数据。当前数据代表一个 `as_of_date` 下的物业组合快照，不在本项目中实现多月份历史库。

因此应用应遵守以下原则：

- 所有页面明确显示 `Data as of`，避免把静态快照描述成实时数据。
- Unit Availability 表示“根据最新导入 Rent Roll 动态计算”，而不是实时连接物业管理系统。
- 当前版本不提供月环比、同比或历史趋势结论。
- 跨物业排名、分布和异常比较属于同一时间点的横截面分析，可以正常展示。
- 趋势能力只作为未来扩展说明保留，不使用单月数据伪造趋势图。

### 2.2 日期格式

数据库、CSV 标准化结果、后端计算和 API 使用统一的规范日期格式：

```text
YYYY/MM/DD
```

月份字段使用：

```text
YYYY/MM
```

前端展示时再转换为美式格式：

```text
MM/DD/YYYY
```

例如数据库中的 `2026/02/25` 在页面显示为 `02/25/2026`。排序、筛选、时间窗口计算和 What-if 模型必须使用规范日期值，不能使用展示字符串参与计算。

### 2.3 指标命名边界

- Rent Roll 中的 Charge Amount 表示 scheduled charge，不代表已经收到的现金。
- Resident Balance 只称为 balance exposure，不在未确认业务定义时直接称为 delinquency。
- What-if 输出称为 scheduled rent impact，不称为 NOI、利润或现金流影响。
- Market Rent 与当前 Rent Charge 的差额称为 loss-to-lease opportunity，不直接称为确定可实现的收入。

## 3. 从 Rent Roll 动态生成 Availability

Unit Availability 的统计值不单独存储，也不依赖 Unit Availability 报表中的聚合结果。后端根据当前 Rent Roll 快照、单元状态、当前住户和 Future Resident 动态生成。

### 3.1 单元基础状态

`residential_units.status` 包含：

| 状态 | 含义 | 是否属于当前住户占用 |
| --- | --- | --- |
| `OCCUPIED` | 单元存在当前 Resident | 是 |
| `VACANT` | 当前没有 Resident | 否 |
| `MODEL` | 样板单元 | 否 |
| `DOWN` | 暂不可用单元 | 否 |
| `ADMIN` | 管理用途或非收入单元 | 否 |

`MODEL`、`DOWN` 和 `ADMIN` 是单元状态，不创建伪 Resident，也不计入普通 Occupied 或 Vacant。

### 3.2 Availability 分类

| 指标 | 动态计算规则 |
| --- | --- |
| `occupied_no_notice` | `OCCUPIED` 且当前 Resident 没有 `move_out_date` |
| `vacant_rented` | `VACANT` 且同一物业、同一单元存在有效 Future Resident |
| `vacant_unrented` | `VACANT` 且没有有效 Future Resident |
| `notice_rented` | `OCCUPIED`，当前 Resident 有 `move_out_date`，且同一单元存在有效 Future Resident |
| `notice_unrented` | `OCCUPIED`，当前 Resident 有 `move_out_date`，且没有有效 Future Resident |
| `model` | `status = MODEL` |
| `down` | `status = DOWN` |
| `admin` | `status = ADMIN` |

Future Resident 需要与当前单元的 `property_code + unit_code` 对应。系统使用 `BOOKING_STALE_DAYS` 排除明显过期的 Future Resident 记录，默认窗口为 90 天。

### 3.3 汇总公式

```text
occupied = occupied_no_notice + notice_rented + notice_unrented

vacant = vacant_rented + vacant_unrented

avail = notice_unrented + vacant_unrented

occ_pct = occupied / total_units

occ_w_non_rev_pct = (occupied + model + down + admin) / total_units

leased_pct = (total_units - vacant_unrented) / total_units
```

所有百分比统一保留两位小数。`total_units = 0` 时百分比返回 0，并在展示层避免绘制没有意义的比例图。

### 3.4 数据质量检查

每次开发者导入后应输出或验证：

- 每个物业的状态分类合计是否等于 `total_units`。
- `OCCUPIED` 单元是否都有当前 Resident。
- `VACANT / MODEL / DOWN / ADMIN` 是否错误关联当前 Resident。
- Future Resident 是否能匹配有效的物业和单元。
- 日期是否全部符合 `YYYY/MM/DD`。
- `move_out_date` 是否早于或等于后续 Future Resident 的 `move_in_date`。
- Availability 派生结果是否存在负数、空值或超过 100% 的比例。

原始 Unit Availability 报表可以作为一次性对账参考，但不作为应用指标的事实来源。

## 4. 信息架构

MVP 保持四个主要页面，避免为每一种实体和图表建立独立页面。

| 页面 | 路由 | 主要目的 |
| --- | --- | --- |
| Portfolio Overview | `/portfolio` | 查看整个物业组合的经营快照和优先事项 |
| Lease Risk | `/lease-risk` | 查看未来租约到期、Move-out 和相关租金暴露 |
| Property Detail | `/properties/:propertyCode` | 下钻到单个物业的 Availability、租约和租金结构 |
| What-if | `/what-if` | 对选定物业或租约到期 cohort 运行情景模拟 |

Morning Brief 放在 Portfolio Overview 顶部，不单独建立页面。Unit 和 Resident 明细使用抽屉或详情面板展示，不扩展成住户管理系统。

## 5. Portfolio Overview

### 5.1 页面目标

让资产经理在一分钟内回答：

- 当前组合有多少单元，多少可租，多少处于 Notice 状态？
- 哪些物业的可租库存和租金暴露最高？
- 未来 30、60、90 天有多少租约到期？
- 哪些物业最值得优先下钻？

### 5.2 顶部信息

页面顶部固定展示：

- `Data as of MM/DD/YYYY`
- 数据覆盖物业数量
- 数据覆盖单元数量
- 当前数据月份
- 数据质量提示数量

### 5.3 核心 KPI

| KPI | 定义 |
| --- | --- |
| Total Units | 所有物业住宅单元总数 |
| Physical Occupancy | `occupied / total_units` |
| Leased Percentage | `(total_units - vacant_unrented) / total_units` |
| Available Units | `notice_unrented + vacant_unrented` |
| Vacant Unrented Exposure | `vacant_unrented` 单元的 Market Rent 合计 |
| Expiring in 60 Days | 截至 `as_of_date + 60 days` 的有效 Lease 数量 |

首页保持 5 至 6 个 KPI，不堆叠所有可计算字段。

### 5.4 主要可视化

1. **Availability Composition**：使用堆叠条形图展示各物业的五类核心状态，支持按单元数和百分比切换。
2. **Property Priority Table**：展示物业、总单元、Avail、Occupancy、Leased%、未来 60 天到期、空置市场租金暴露。
3. **Lease Expiration Buckets**：仅展示当前快照推导出的未来 30/60/90/180 天到期数量，不称为历史趋势。
4. **Morning Brief**：显示三至五条有数据依据的风险、机会和建议查看方向。

物业数量较多时，Priority Table 比大量小型饼图更容易比较。Charge Code 饼图不放在 Portfolio 首页。

## 6. 库存与 Availability 分析

“库存”指当前没有产生正常占用、或即将可租的单元，不把所有非 Occupied 状态简单合并。

页面和指标应区分：

- `vacant_unrented`：立即可租但尚未预租，是最直接的去化目标。
- `notice_unrented`：当前仍 Occupied，但已知将搬出且尚无后续 Resident，是未来库存。
- `vacant_rented`：当前空置但已有 Future Resident，主要关注 Move-in 时间和空置间隔。
- `notice_rented`：已知搬出且已有后续 Resident，主要用于检查衔接情况。
- `model / down / admin`：非普通租赁库存，单独展示，不混入可租库存。

物业优先级可使用一个透明的排序分数，但页面必须同时展示原始指标。第一版建议直接按 `vacant_unrented market rent exposure` 排序，不引入难以解释的综合模型。

## 7. Lease Risk Dashboard

### 7.1 分析对象

以当前 `as_of_date` 为起点，根据 `lease_end_date` 生成未来到期 cohort：

- 0 至 30 天
- 31 至 60 天
- 61 至 90 天
- 91 至 180 天
- 已过期但仍为当前 Resident
- 缺失 Lease Expiration Date

### 7.2 筛选条件

- Property
- Lease expiration bucket
- Unit type
- 是否存在 `move_out_date`
- Balance 是否为正
- Market Rent 与 Scheduled Base Rent 差额范围

### 7.3 结果字段

| 字段 | 用途 |
| --- | --- |
| Property / Unit | 定位风险单元 |
| Lease Expiration | 计算到期窗口 |
| Move-out Date | 区分已知搬出和一般到期 |
| Market Rent | 估算市场租金暴露 |
| Scheduled Base Rent | 从映射后的基础租金 Charge Code 汇总 |
| Loss-to-lease | `market_rent - scheduled_base_rent` |
| Balance | 作为额外关注信号，不直接定义为欠租 |
| Availability Status | 连接到当前单元状态和 Future Resident 情况 |

风险列表顶部的总数和总金额必须与筛选后的明细完全一致。用户可以将当前筛选结果直接带入 What-if 页面。

## 8. Market Rent 与 Charge Code

### 8.1 Market Rent 分析

对每个 Occupied 单元比较：

```text
loss_to_lease = market_rent - scheduled_base_rent

loss_to_lease_pct = loss_to_lease / scheduled_base_rent
```

需要先维护明确的 Charge Code 分类，只有被标记为基础租金的项目才能进入 `scheduled_base_rent`。Utilities、Parking、Storage、Subsidy、Concession 等不能自动与基础租金混合。

输出包括：

- 正 loss-to-lease 单元数量和金额。
- Market Rent 低于 Scheduled Base Rent 的异常或溢价单元。
- 按物业和 Unit Type 的平均差额。
- 数据覆盖率，即有 Market Rent 且能识别 Base Rent 的单元比例。

### 8.2 Charge Code 展示

Charge Code 是辅助分析，不作为 MVP 的独立主页面。

- Portfolio 层使用按类别聚合的堆叠条形图。
- Property Detail 可展示该物业的 Charge Code 构成。
- 只有选中单个物业且类别较少时才使用环形图。
- 小型物业只有一个主要 Charge Code 时，直接显示金额和占比，不绘制无信息量的饼图。

## 9. What-if 模型

### 9.1 模型目标

针对未来一段时间内到期的 Lease，估算不同续租和换租假设对 scheduled rent 的影响。模型是决策辅助工具，不是预测模型。

### 9.2 输入

| 输入 | 说明 | 示例默认值 |
| --- | --- | --- |
| Analysis horizon | 模拟窗口 | 12 个月 |
| Renewal rate | 到期 Resident 的假设续租率 | 70% |
| Renewal rent change | 续租后的租金变化 | 3% |
| New lease vs market | 新租相对 Market Rent 的溢价或折价 | 0% |
| Average vacancy months | 未续租后的平均空置期 | 1.5 个月 |

用户先选择物业、Unit Type 或 Lease Expiration cohort，再调整假设。已明确存在 Move-out Date 的 Resident 可以固定视为不续租，或由用户决定是否覆盖该规则。

### 9.3 计算

对每个进入 cohort 的单元定义：

```text
R = 当前 Scheduled Base Rent
M = Market Rent
L = Lease 到期后仍落在分析窗口内的月份数
p = Renewal Rate
g = Renewal Rent Change
m = New Lease vs Market
v = Average Vacancy Months
```

```text
renewal_revenue = p * L * R * (1 + g)

new_lease_revenue = (1 - p) * max(0, L - v) * M * (1 + m)

scenario_revenue = renewal_revenue + new_lease_revenue

baseline_revenue = L * R

scheduled_rent_impact = scenario_revenue - baseline_revenue

vacant_unit_months = (1 - p) * min(v, L)
```

### 9.4 输出

- Baseline Scheduled Rent
- Scenario Scheduled Rent
- Scheduled Rent Impact
- Expected Renewed Units
- Expected Turnover Units
- Vacant Unit-months
- 受影响单元和物业数量
- Base Rent 与 Market Rent 数据覆盖率
- 所有输入假设和排除记录数量

### 9.5 模型校验

- `renewal_rate = 100%` 且 `renewal_rent_change = 0%` 时应回到续租基线。
- 其他输入不变时，增加 vacancy months 不能提高 Scenario Scheduled Rent。
- Cohort 明细金额合计必须等于结果总额。
- 缺少 Market Rent 或 Base Rent 的记录不能静默填零，必须排除并展示覆盖率。
- LLM 只能解释模型输出，不能修改公式或重新计算金额。

## 10. Morning Brief 与 LLM 分析工具

### 10.1 Morning Brief 定位

由于数据库只有单月快照，Morning Brief 不描述“相比昨天”或“相比上月”的变化。它表示每次打开最新导入快照时，对当前组合状态的自动摘要。

Brief 建议包含：

- 当前 Available Units 最多或租金暴露最高的物业。
- 未来 60 天 Lease Expiration 最集中的物业。
- `vacant_unrented`、`notice_unrented`、`down` 等值得关注的状态。
- Market Rent 与 Scheduled Base Rent 差额较大的物业。
- 数据缺失和口径异常。
- 可点击的下钻入口或建议运行的 What-if 情景。

### 10.2 计算与生成流程

```text
SQLite
  -> 后端确定性统计工具
  -> Brief Facts JSON
  -> LLM 排序和自然语言表达
  -> 前端展示事实、范围和链接
```

LLM 不直接访问数据库，不拼接任意 SQL，也不自行计算核心 KPI。

### 10.3 白名单工具

```text
get_portfolio_summary
get_availability_breakdown
get_lease_expirations
get_balance_exceptions
get_rent_gap_summary
get_property_summary
run_lease_expiry_scenario
```

每个工具返回：

- `as_of_date`
- 输入筛选条件
- 指标值
- 指标定义
- 数据覆盖率
- 数据质量提示
- 可追溯的物业或单元引用

### 10.4 LLM 边界

LLM 可以：

- 选择合适的白名单工具和参数。
- 比较物业、排序风险、总结工具输出。
- 解释 What-if 输入变化为何影响结果。
- 在数据不足时明确说明无法回答。

LLM 不可以：

- 猜测 Resident 搬出的原因或真实续租概率。
- 把 Balance 自动判断为 delinquency。
- 生成 NOI、估值、IRR 或投资建议。
- 查询或展示回答问题不需要的 Resident 级字段。
- 在工具失败或没有数据时编造数字。

模型不可用时，应用仍显示由规则模板生成的 Morning Brief。

## 11. 趋势能力的简化保留

当前数据库只有单月份，MVP 不实现历史趋势计算。为了向面试官展示已经考虑时间序列问题，采用以下方式保留趋势设计：

1. Portfolio 页面显示一个简洁的 `Trend readiness` 说明或不可用状态，明确写出 `Historical comparison requires additional monthly snapshots`。
2. API 响应始终包含 `as_of_date` 和 `month_year`，使指标语义具备时间边界。
3. 文档说明未来可将每月快照写入独立历史表或分析仓库，但不在当前 SQLite Schema 中预建未使用的多月结构。
4. 面试演示中明确区分横截面比较和时间趋势，避免用物业之间的差异代替历史变化。

未来获得多月数据后，可扩展但当前不实现的指标包括：

- Occupancy 和 Leased% 月度变化。
- Available Units 的新增、去化和平均空置周期。
- Lease renewal rate。
- Market Rent 和 Scheduled Base Rent 的月度变化。
- Balance exposure 的变化。

## 12. API 规划

现有实体查询 API 可继续支持调试和明细下钻。前端主要使用后端聚合 API，避免下载全部 Resident 和 Rent Roll 后在浏览器计算指标。

| API | 方法 | 用途 |
| --- | --- | --- |
| `/api/availability` | GET | 当前所有物业的动态 Availability |
| `/api/portfolio/summary` | GET | Portfolio KPI、数据日期和质量提示 |
| `/api/lease-risks` | GET | 按窗口和物业筛选 Lease Risk |
| `/api/properties/:code/summary` | GET | 单物业聚合信息 |
| `/api/rent-gap` | GET | Market Rent 与 Base Rent 差额 |
| `/api/morning-brief` | GET | 确定性 Brief Facts 和模板摘要 |
| `/api/scenarios/lease-expiry` | POST | 执行确定性 What-if 模型 |
| `/api/assistant/query` | POST | 通过白名单工具回答受限问题 |

聚合 API 建议使用统一响应结构：

```json
{
  "as_of_date": "2026/02/25",
  "month_year": "2026/02",
  "filters": {},
  "metrics": {},
  "definitions": {},
  "coverage": {},
  "data_quality": []
}
```

## 13. 技术实现建议

| 层级 | 建议 |
| --- | --- |
| Frontend | React + TypeScript + Vite |
| Visualization | Apache ECharts 或 Recharts，选择一种即可 |
| Backend | 保留 Express + TypeScript |
| Database | 保留单月 SQLite |
| Validation | API 输入 Schema 校验和统一错误响应 |
| Analysis | SQL 聚合加可测试的 TypeScript 计算函数 |
| LLM | 支持 Function Calling 的模型，只暴露白名单工具 |
| Deployment | 单个演示环境，前端和 API 同源部署 |

招聘 Case Study 不需要微服务、消息队列、数据仓库或复杂权限系统。代码重点应放在数据口径、可测试计算、清晰 API 和完整用户路径。

## 14. 分阶段实施

### Phase 0：数据与口径收尾

- 将 CSV 转换结果、数据库日期和后端配置统一为 `YYYY/MM/DD`。
- 将 `month_year` 统一为 `YYYY/MM`。
- 更新 Availability 查询中的日期比较逻辑，不再依赖 `MM/DD/YYYY` 字符串切片。
- 完成 Availability 分类、Future Resident 匹配和零单元物业的边界检查。
- 建立 Base Rent Charge Code 映射。
- 增加导入后的数据质量报告。

验收标准：所有日期可解析；每个物业的状态合计等于总单元数；Availability 结果可由明细复核；重复 Seed 得到一致结果。

### Phase 1：Portfolio Overview

- 建立 React 应用框架和统一页面布局。
- 实现 Portfolio Summary 和 Availability 聚合 API。
- 完成 KPI、Availability 堆叠图、物业优先级表和数据质量提示。
- 展示 Data as of 和单月数据限制。

验收标准：页面 KPI 与 API、SQL 明细一致；可以从 Portfolio 下钻到物业；无伪趋势图。

### Phase 2：Lease Risk 与 Property Detail

- 实现 30/60/90/180 天 Lease Expiration cohort。
- 实现物业、Unit Type、Move-out 和 Balance 筛选。
- 建立 Base Rent 和 loss-to-lease 分析。
- 从风险列表进入单物业和 What-if。

验收标准：筛选后的 KPI 与明细合计一致；日期边界有自动化测试；缺失数据明确展示。

### Phase 3：What-if

- 将情景公式实现为独立、确定性的 TypeScript 函数。
- 提供 Scenario API 和交互式输入面板。
- 展示基线、情景、差额、覆盖率和受影响 cohort。
- 为公式边界和单调性增加测试。

验收标准：模型满足校验规则；所有结果可回溯到输入、cohort 和公式；不输出 NOI 或预测性结论。

### Phase 4：Morning Brief 与 LLM

- 先实现不依赖 LLM 的 Brief Facts 和模板摘要。
- 增加白名单工具调用和受限问答。
- 为常见问题建立固定评测集。
- 增加工具失败和模型不可用时的 fallback。

验收标准：所有数字与工具输出一致；没有任意 SQL；数据不足时不编造答案；LLM 关闭后核心应用仍可使用。

## 15. 面试演示脚本

控制在三至五分钟：

1. 打开 Portfolio，说明数据是单月快照，并展示动态 Availability。
2. 使用物业优先级表找到 `vacant_unrented exposure` 或 60 天到期风险最高的物业。
3. 进入 Lease Risk，展示风险 cohort、Rent Gap 和明细可追溯性。
4. 将当前 cohort 带入 What-if，调整 Renewal Rate、Rent Change 和 Vacancy Months。
5. 展示 Scheduled Rent Impact，并解释公式边界和数据覆盖率。
6. 回到 Morning Brief，说明 LLM 只负责调用工具和解释确定性结果。
7. 展示 Trend Readiness 说明，明确单月数据不能支持真实趋势，但接口和产品语义已保留时间边界。

## 16. 非目标

MVP 明确不做：

- 多月份历史数据库和真实趋势图。
- Resident CRM、缴费、维修工单和消息系统。
- 面向业务用户的 Excel 上传和字段映射界面。
- 多租户、企业 SSO 和复杂角色权限。
- 机器学习续租预测。
- 自动 SQL Agent、RAG、向量数据库或多 Agent 系统。
- NOI、IRR、Cap Rate、DCF 和资产估值模型。
- 使用单月快照推断因果关系或市场走势。

本项目的判断标准不是功能数量，而是指标可信、结果可追溯、情景可解释、LLM 有边界，以及端到端演示能够清楚表达业务价值。
